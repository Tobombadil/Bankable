# services/social — syndication pipeline (Sprint 2)

Scope, per `.claude/agents/content-social.md` and the Sprint 2 task brief: the pipeline **up to
but not including actually posting to any network**. No social accounts exist yet — the owner
creates them per `docs/32-social-operating-playbook.md` §2. Everything here stops at a dry-run
preview of what would be sent.

## Modules

- **`models.py`** — `PostDraft` (pre-publish: draft/approved/rejected/scheduled/withdrawn) and
  `Post` (a frozen publish outcome, always `dry_run=True` in this package), plus `ReviewMetadata`
  and `ValidationResult`. Docs/21 §3.18 `post` entity, split into the two shapes the task brief
  asks for. JSON round-trippable (`to_dict`/`from_dict`) for `queue.py`'s store.
- **`editorial.py`** — `SocialEvent` (the structured-field contract of docs/32 §3.2), the docs/32
  §3.1 eligibility rules (`channels_for_event`), the per-channel templates of §3.3
  (`render_proposal_new`, ... `render_digest_weekly`), the §4.3 hard validation gates
  (`validate_draft`), attribution/disclosure/lag-notice builders, and `build_draft`/
  `draft_events` (the `event → draft` pipeline stage). Also the `from_diff_row` adapter from
  `pipeline/diff.py`'s prototype event shape (see "Known gap" below).
- **`queue.py`** — `ReviewQueue`, a JSON-file-backed review queue: `add_draft` (with docs/32 §4.8
  duplicate suppression: idempotency key, cross-event 7-day window with the withdrawn > status
  changed > new priority order, and a 30-day content-hash guard), `list_drafts`/`approve`/
  `reject`/`edit`, `expire_stale` (the §4.4 SLA clock), scheduling stubs (`schedule`,
  `next_available_slot`, `check_rate_limit` against the §4.7 "our ceiling" column), and
  `graduation_status` (the §4.6 auto-publish gate — always refuses; LinkedIn refuses
  unconditionally by decision).
- **`publishers/`** — `Publisher` (abstract) plus `BlueskyPublisher`, `LinkedInPublisher`,
  `XPublisher`. All three are dry-run only. Bluesky alone has a `feature_flag_live` switch for a
  future AT Protocol app-password flow; even with the flag on, it refuses without
  `BSKY_HANDLE`/`BSKY_APP_PASSWORD` in the environment and then raises `NotImplementedError` (no
  network call is wired — no account exists yet). LinkedIn and X have no live path at all in
  Sprint 2.
- **`__main__.py`** — the CLI: `draft`, `review list|approve|reject`, `dry-run`, `report`.

## CLI

```
python -m services.social draft --events <parquet> [--records <parquet>] [--queue-path PATH]
python -m services.social review list [--channel C] [--status S]
python -m services.social review approve <draft_id> --reviewer <email>
python -m services.social review reject <draft_id> --reviewer <email> --reason <code>
python -m services.social dry-run <bluesky|linkedin|x>
python -m services.social report
```

`draft` accepts two event-parquet shapes:

1. **The target contract** — one row per `editorial.SocialEvent` field (what a real `event` store
   built to docs/21 §3.10 will eventually emit).
2. **`pipeline/diff.py`'s prototype shape** — `event_type, record_id, source_id, field, before,
   after, observed_at`, one row per *changed field*. The CLI joins this against `--records` (the
   canonical snapshot from `pipeline/normalize.py`) and `data/sources.yaml` (read-only) to recover
   capacity/technology/place/provenance. `capacity_change`, `cod_change` and `removed` rows are
   dropped (never postable per docs/32 §3.1); `new`/`status_change`/`withdrawn` are mapped to
   `proposal.*` or, for opportunity-category sources, the closest analogue. A record-less `new`
   row (no `--records` match) has no size field and correctly never earns a post — thresholds are
   never guessed.

## Known gap: source id mismatch between `pipeline/diff.py`'s demo output and `data/sources.yaml`

`pipeline/diff.py --demo` (and `data/eval/events.parquet`, generated by it) writes short
connector-internal ids (`caiso`, `ercot`, `spp`, `nyiso`, `isone`, `eia860m`) into `source_id`,
while `data/sources.yaml`'s ids are the long canonical form (`us.iso.caiso.gen_queue`, ...). This
package's `_load_source_meta()` reads `sources.yaml` verbatim (read-only, per this task's write
scope) and cannot resolve those short ids, so running `draft` directly against
`data/eval/events.parquet` today yields zero drafts — not a bug in the eligibility logic, but a
naming seam between the Sprint 1 prototype and the source registry. Confirmed by re-running the
same join with a manual six-entry alias table (not shipped — a demonstration only):

```
170 diff.py events -> 170 SocialEvents (new/status_change/withdrawn only) -> 176 drafts
Counter({('bluesky','proposal.status_changed'): 36, ('x','proposal.status_changed'): 36,
         ('bluesky','proposal.withdrawn'): 20, ('x','proposal.withdrawn'): 20,
         ('bluesky','proposal.new'): 19, ('x','proposal.new'): 19,
         ('linkedin','proposal.new'): 13, ('linkedin','proposal.withdrawn'): 9,
         ('linkedin','proposal.status_changed'): 4})
```

Whoever builds the real `event` table (docs/21 §3.10) should emit the canonical `source_id`
directly, which removes the need for any alias table.

## Editorial decisions recorded as assumptions (not re-derivations of docs/32)

- **High-volume ISOs** for the "≥100 MW for solar/storage" bar (docs/32 §3.1): CAISO, ERCOT, SPP,
  MISO — the four largest queues per `docs/22` §1. Not named explicitly in `docs/32`.
- **Disclosure text** (`DISCLOSURE_TEXT`, task item 2): the docs/13 §6.5 "Automated social
  account" bio line for Bluesky and X; for LinkedIn (which never auto-publishes, docs/32 §1.4,
  §4.6), the human-review statement from the same table, since the Art. 50(4) exemption is what
  makes LinkedIn's manual-review policy sufficient. Carried as a `PostDraft.disclosure_text`
  field (audit metadata, matching docs/21 §3.18 `disclosure_label`) rather than appended inline
  to every body — the §3.3 templates verbatim have no disclosure clause; disclosure is an
  account-level bio/About statement in docs/32 §2.2, not a per-post one.
- **Attribution substring** (`attribution_line_for`): `"Source: {source_name}"` for every event
  type except `funding.cancelled`/`reinstated`, whose §3.3 template instead reads "... per
  {source_name} record dated ..."; the bare source name is what's common to both phrasings and is
  what the §4.3 gate 3 check ("contains the attribution line ... unchanged") is verified against.
- **`digest.weekly`** is exempt from the attribution-line and number-traceability gates (§4.3
  gates 3 and 5): it is a roll-up over `digest_items`, not a single-source, single-fact post, and
  its own §3.3 template has no `Source:` clause. Every other gate still applies.
- **Never-posted default-deny**: any `event_type` not in `POSTABLE_EVENT_TYPES` earns no post on
  any channel, including a `pipeline/diff.py` `removed` row (ambiguous — could mean withdrawn,
  cancelled, or a source hiccup — so it is never guessed into a post).
- **RFP/award/funding org and title fields are effectively required**, not omittable, once an
  event reaches that template: the fact line is meaningless without `issuer_org`/
  `solicitation_title`/`awardee_org`. `channels_for_event` already requires `awardee_org` for
  `opportunity.awarded`; the others are assumed present in every source-of-record RFP/award/grant
  entry.

## Tests

`tests/test_social_models.py`, `tests/test_social_editorial.py`, `tests/test_social_queue.py`,
`tests/test_social_publishers.py`, `tests/test_social_cli.py` — 138 tests. Coverage:

- Every entry in `POSTABLE_EVENT_TYPES` (a synthetic `SocialEvent` fixture per event type) earns a
  draft on at least one channel, fits its channel's character limit, and passes every §4.3 gate.
- Threshold edges (exact bar, high-volume-ISO bar, LinkedIn bar, load/voltage/capex alternates,
  "no size field at all never posts"), canonical-transition gating, RFP-closing's 14/3-day
  windows, awarded requiring a named awardee, restricted/unknown source denial, and the
  never-posted default-deny for made-up or field-level event types.
- Attribution and disclosure present on every draft; the lag notice present on proposal events and
  absent on live (opportunity/funding) ones; null fields omitted, never rendered as `"None"`;
  withdrawal reason quoted verbatim when present.
- Deterministic overflow handling: optional clauses drop before the mandatory fact/URL/attribution
  tail, and a body that still overflows after every optional clause is gone falls back to
  truncating the fact line — always fitting, always keeping `page_url` and attribution intact.
- Each hard gate's failure mode individually (banned words, unsolicited `@mention`, a stray URL, an
  invented number, a restricted `reuse_class`, missing disclosure).
- `idempotency_key`/`dedupe_key` stability and the withdrawn > status_changed > new priority order
  (`rfp_closing` always outranks).
- The `pipeline/diff.py` adapter: `capacity_change`/`cod_change`/`removed` rows dropped, a `new`
  row correctly joined to its canonical record, and a record-less `new` row never inventing a
  size to clear the threshold.
- The review queue: idempotency-key, cross-event-window (with priority override) and content-hash
  duplicate suppression; approve refuses on failed validation; reject requires a known reason
  code; edit stores a diff and re-validates; SLA expiry per channel; scheduling requires prior
  approval and respects the daily ceiling; **graduation always refuses** (LinkedIn unconditionally,
  everyone else on the 200-post/30-day/edit-rate/wrong_fact criteria); JSON persistence round-trips
  through a fresh `ReviewQueue` instance.
- Publishers: dry run never touches the network and reports the exact payload; Bluesky's
  `feature_flag_live` defaults off and even when on refuses without both credentials, then raises
  `NotImplementedError` rather than silently sending; LinkedIn and X always refuse a live call;
  the shared `validate()` gate catches a wrong-channel or unapproved draft.
- The CLI: `draft` end to end against a `diff.py`-shaped parquet (including the below-threshold
  record correctly earning nothing), idempotent on rerun; `review list/approve/reject`; `dry-run`
  previews without mutating draft state; `report` prints every docs/32 §6.2 section.

## Draft generation from the event log (Sprint 3)

**What.** `services/social/worker.py` (`draft_posts_tick`, the exact contract `infra/scheduler`
wires up — name and signature fixed by the task brief) and `services/social/db_events.py`
(`social_event_from_db`, the bridge from `services.db.models.Event` to `editorial.SocialEvent`)
turn the real, append-only `event` table into rows in the real `post` table
(`services.db.models.Post`) — the admin review queue's `GET /admin/v1/posts` reads that table
directly (`services/api/admin_posts.py`). One tick: read `event` rows past the watermark, map
each through `db_events.social_event_from_db`, run the docs/32 §4.3 hard gates this module owns,
then call `editorial.channels_for_event` + `editorial.build_draft` per channel exactly as Sprint 2
built them — nothing here reimplements a template, a threshold, or a validation gate. Nothing
here ever calls a network adapter; every row lands `state="draft"`, or `state="approved"` with
`auto_published=True` when `ChannelConfig.auto_publish` is on for that channel — publishing is a
later job, unchanged from Sprint 2's standing scope line.

**How this relates to `queue.py`'s file-backed `ReviewQueue`.** They are two independent, parallel
drafting paths writing to two independent stores, not a migration of one into the other:

- `queue.ReviewQueue` (Sprint 2) drafts from a one-off parquet file — either the target
  `editorial.SocialEvent` shape, or `pipeline/diff.py`'s prototype diff-row shape via
  `editorial.from_diff_row` — into a local JSON file. It has no notion of a database, a `post`
  table, or a watermark; its own `PostDraft`/`Post` dataclasses (`services/social/models.py`) are
  distinct types from `services.db.models.Post`, on purpose (this task's write scope explicitly
  forbids editing `queue.py` beyond reusing two of its names).
- `worker.draft_posts_tick` (Sprint 3, this section) drafts from the real `event` table into the
  real `post` table the admin panel and (eventually) a publisher job read.
- **`queue.py` stays** for exactly the path its own module docstring already names: a one-off,
  offline dry run against a `pipeline/diff.py`-shaped parquet (the CLI's `draft` command,
  `services/social/__main__.py`, untouched by this task) — useful for testing templates and
  thresholds against Sprint 1 prototype data before a real `event` row exists for it, or for a
  manual backfill. It is not wired into the scheduler and this task does not retire it; whoever
  eventually retires `pipeline/diff.py`'s prototype shape (services/README.md's own "known gap"
  entry) is the natural point to retire `queue.py` alongside it, not before.
- The two paths share only what both were told to reuse verbatim: `queue._content_hash` (the
  content-hash string-normalisation rule) and, by contract, nothing else — `worker.py` does not
  import `queue.ReviewQueue`, `PostDraft`, or `Post`, and a post drafted by one path is invisible
  to the other's duplicate suppression (different stores). A proposal drafted once via the CLI's
  offline `queue.json` and again via a real `event` row can, in principle, both post — this is the
  same seam the "Known gap: source id mismatch" section above already describes for the CLI path,
  not a new one this task introduces.

**Decisions** (numbered; each is an interpretation of the task brief where the brief and the
current schema/tests did not fully settle it on their own):

1. **Event-type mapping is the literal table in the task brief, not the full docs/21 §7.3
   vocabulary.** The brief lists `created`, `status_change`, `withdrawn`/`cancelled` for proposals
   and `announced`/`opened`, `closing`/`due_date_changed`, `awarded`, `cancelled`/`reinstated` for
   opportunities, "anything else -> `None`". docs/21 §7.3's Proposal lifecycle group also lists
   `filed`, `studied`, `permitted`, `contracted`, `built` as event types in their own right (as
   opposed to values folded into a `status_change` event's `before`/`after`); no connector emits
   them today (`services/ingest/loader.py`'s `DIFF_EVENT_TYPE_MAP` only ever writes `created`,
   `status_change`, `withdrawn`, `capacity_changed`, `field_changed`), and the brief's own table
   does not name them, so `db_events._PROPOSAL_EVENT_TYPE_MAP` does not either — extending past the
   brief's literal list was judged more likely to silently draft something docs/32 never asked for
   than to miss a real event type. Same reasoning for opportunities: docs/21 §7.3 spells the
   deadline-passed state `closed`, not the brief's word "closing"; `db_events` accepts `closed`,
   `due_date_changed`, and (defensively, free) the literal spelling `closing`, all three mapping to
   `opportunity.rfp_closing`.
2. **The four hard gates (docs/32 §4.3, US-801 AC3) live in `worker.py`, not `db_events.py`.**
   `db_events.social_event_from_db` only ever maps or returns `None`; it never queries whether the
   subject is visible, whether the licence permits derived publication, or whether the event is
   published. This keeps the "is this event a candidate at all" question (mapping, in
   `db_events.py`) separate from the "may we actually post it" question (gating, in `worker.py`),
   matching the task brief's own file-ownership split. `worker._passes_hard_gates` reuses
   `services.api.visibility.proposal_visibility_filter`/`opportunity_visibility_filter` with
   `entitlement="api"` exactly as instructed, plus two checks the visibility filter does not make:
   `event.published_at is not None` (the *event's* own column, distinct from the subject's
   `published_at`/`public_at` the visibility filter already reads) and `event.licence.
   allows_derived_publication` (a `Licence` boolean the visibility filter does not check at all —
   it only checks `reuse_class`). The fourth named gate, "the record must not be `unpublished`", is
   checked explicitly too even though `publish_state == "public"` (already required by the
   visibility filter) already rules it out under the current `RECORD_PUBLISH_STATES` vocabulary —
   kept as an explicit, named check per the brief's own enumeration, not merged away, in case the
   two ever decouple.
3. **A missing-required-field opportunity event is `None` from `db_events.py`, not a gate skip.**
   `opportunity.awarded` and `funding.cancelled`/`funding.reinstated` need `awardee_org`,
   `award_usd`, and `funding_program` — none of which exist as a column on `Opportunity`
   (`services/db/models.py`) or are ever written into `Event.after` by any connector wired so far
   (grepped; confirmed absent). `editorial.render_funding_change` and the award template embed
   these fields unconditionally (no omittable clause, unlike every other clause in docs/32 §3.3's
   templates), so passing `None` through would print the literal word "None" into a real post —
   "never invent a value" (docs/32 §3.4) reads as "never emit this template at all" when a
   non-omittable field is absent, not as a hard gate (those are specifically the four in decision
   2, all about *whether we may post*, not *whether we have enough to say*). `db_events.py` returns
   `None` for these before the worker ever sees them; `posts_skipped_gate` does not count them, and
   `channels_for_event`'s own `awardee_org`-truthy check for `opportunity.awarded` never runs
   because the event never reaches it. Concretely: **no post is ever drafted for `opportunity.
   awarded`, `funding.cancelled` or `funding.reinstated` yet** — a real schema gap upstream of this
   task's write scope (`services/db/models.py`, out of scope), not a bug in this mapping. Same
   reasoning, same file, guards `opportunity.rfp_opened`/`rfp_closing`/`awarded` on `issuer_org`
   being present (`Opportunity.issuer_org_id` is nullable) since those templates also embed it
   unconditionally.
4. **`page_url` stays bare; the UTM parameters live only on `post.link_url`.** `editorial.
   SocialEvent.page_url` is the same bare `f"{WEB_HOST}/proposals/{slug}"` `db_events.py` builds
   from the record's own slug, with no query string — `editorial.render`/`validate_draft` are
   unmodified from Sprint 2 and their gate 2 ("`page_url` appears in the body exactly once") is
   checked against that exact string, so decorating it would either fail that gate or require
   editing `editorial.py` (out of scope by preference). `worker._utm_link` builds the docs/32 §3.2
   item 3 UTM string (`utm_source`/`utm_medium`/`utm_campaign`/`utm_content`) once, only when
   writing `Post.link_url` — the body a reader sees still carries the plain page link;
   `Post.link_url` is what a click-through/attribution job would actually dereference. The
   content-hash duplicate check (`worker._is_content_duplicate`) strips the UTM query string back
   off a stored `Post.link_url` (`worker._bare_url`) before comparing, so the hash is computed
   against the same string on both sides of a duplicate check regardless of which row supplied it.
5. **The docs/32 §4.8 content-hash duplicate guard is scoped to the same channel as well as the
   same subject.** The task brief's wording ("a post with the same body content hash ... exists
   for the same subject in the last 7 days") does not mention channel; `queue.py`'s own use of
   `_content_hash` does (`if existing.channel != draft.channel: continue`). Without that same-
   channel scope, `render_proposal_new`'s bluesky and X branches — which render *identical* text,
   differing only in their character limit (§3.3's template has one clause list for both) — would
   flag each other as duplicates of the very two posts one qualifying event is supposed to produce
   on its first tick, which is plainly not the intended behaviour (proved by a test that fails
   without the channel filter and passes with it). `worker._is_content_duplicate` filters on
   `(subject_type, subject_id, channel)`, matching `queue.py`'s precedent over the brief's literal
   wording.
6. **Watermark is a `WorkerWatermark` row (`services/db/models.py`, migration `0006`), advanced
   past every event *examined* this tick, not just posted ones — coordinator-directed revision.**
   The first version of this task computed the watermark as `MAX(event.seq)` over events some
   `post` row references (a join over `post`, no dedicated table). That was correct and permanent
   for any event that earns at least one post, but never advanced past one that earns zero
   (ineligible, gate-skipped, or fully duplicate-suppressed on every channel) — a backlog of more
   than `limit` such events would be rescanned in full on every tick and could starve a genuine,
   later, eligible event behind the page limit forever: a livelock, not merely a "retried a bit
   longer than ideal" limitation, per the coordinator's review. Fixed by reading and writing one
   row, `WorkerWatermark` where `name = "social.draft_posts"`: `_watermark_row` reads it (creating
   it, initialised to the old post-derived `MAX(event.seq)` join, the first time it is missing —
   the coordinator's "an existing deployment keeps its position" requirement, proved by
   `test_bootstraps_watermark_from_post_derived_seq_when_no_row_exists`), and at the end of the
   tick, in the same transaction as the tick's own `post` inserts, its `seq` is set to the highest
   `event.seq` among the events *scanned* this tick (`events[-1].seq`, since they are read in
   ascending `seq` order) — regardless of whether any of them earned a post. Every examined event
   is now passed exactly once: `test_a_large_gated_backlog_does_not_starve_a_later_eligible_event`
   proves 600 events that all fail a gate, followed by one eligible event, with `limit=500` —
   the first tick examines and passes the first 500 (all gated, zero posts, watermark still
   advances to the 500th), the second tick reaches the rest of the backlog and drafts the eligible
   event; `test_watermark_advances_even_when_zero_posts_are_created` proves the row's `seq` moves
   even for a single all-gated tick. The exact `(event_id, channel)` uniqueness check in
   `_process_event`'s per-channel loop is kept as the defensive guard the coordinator asked for —
   with the watermark now advancing past every examined event, it should be even less reachable
   through this worker's own control flow than before (a second worker process, or a manual rerun
   against a stale watermark, are the only paths left to it), so it stays `# pragma: no cover`
   with that reasoning inline rather than a contrived test.
7. **Per-event isolation is a SAVEPOINT (`Session.begin_nested`), not a rollback of the whole
   tick.** One call to `session_factory()` opens one transaction for the whole tick (task brief:
   "everything in one transaction per tick"); each event's processing runs inside its own nested
   transaction so an exception for one event (a missing subject row; a draft that somehow fails its
   own validation gates, kept as a defensive, not-normally-reachable check) rolls back only that
   event's own, possibly-partial writes and is caught and recorded in `errors`, while every other
   event's already-flushed rows survive to the final `db.commit()`. `services/db/test_models.py`
   already proves SQLite supports `begin_nested()` under this project's engine setup; no new
   dependency.
8. **`ChannelConfig.disclosure_label` wins over the draft's own `disclosure_text` when a
   `channel_config` row exists**, per the task brief exactly — `services/api/admin_posts.py`'s
   `admin_set_channel_auto_publish` is the only writer of that column today (a fixed platform
   string, its own decision 4), so in practice this only changes behaviour once an operator has
   turned a channel on; until then every post's `disclosure_label` is `editorial.DISCLOSURE_TEXT[
   channel]`, unchanged from Sprint 2.
9. **`lag_days` is the flat `services.ingest.lag.LAG_DAYS_BY_KIND` constant (14/7), not `lag_days_
   for(...)` with a source's own override.** The task brief says "`lag_days` from `LAG_DAYS_BY_KIND`"
   literally; `Source.lag_days`/`lag_overrides` exist and `lag_days_for` would honour them, but nothing
   in the brief asked `db_events.py` to read the source row for this, and the eight already-listed
   fields it does read from `Event`/`Source`/`Licence` cover everything the brief named. If a source
   ever sets a per-source override, this worker's posts will carry the *class* default lag notice
   text until someone decides `db_events.py` should call `lag_days_for` instead — noted here rather
   than silently guessed at.
